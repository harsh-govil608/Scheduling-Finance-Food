# Document 30: User Testing

## Document Name
User Testing

## Purpose
Define the research methodology, cadence, and organizational process by which every major design decision — new components, new flows, redesigns of existing surfaces — is validated with real users before and after it ships. This document specifies what the completed User Testing program must contain: methodology matrix, recruitment standards, protocol templates, and the feedback loop back into the design system. It is the requirements specification for the program, not the program itself.

## Why It Exists
A design system can be internally consistent, visually polished, and still fail users if it is built and iterated on without continuous contact with the people who actually use it — consistency is not the same thing as usability. This risk is sharper for this product than most: its core differentiator is proactive, unprompted AI action, and there is no accepted design-pattern library for "does the user trust and understand what the AI just did without being asked" the way there is for, say, form validation. This document exists to make research a scheduled, structured discipline rather than an ad hoc activity triggered only when someone senior complains, and to make sure the Phase 1 User Personas' assumptions about behavior are re-verified against real users on a recurring basis rather than trusted indefinitely.

## Approximate Page Count
8-10 pages

## Sections
1. **Testing Methodology Matrix** — the decision tree for which method to use when: moderated vs. unmoderated usability testing, qualitative interviews, diary studies for longitudinal trust behavior, tree testing and card sorting for information architecture, five-second tests for first-impression clarity.
2. **Testing Cadence & Triggers** — the recurring calendar (pre-launch validation gate, quarterly ongoing health checks) plus event-based triggers (any new pillar feature, any redesign of a core-loop surface, any change to a Proactivity Ladder autonomy level) that mandate a testing pass before ship.
3. **Participant Recruitment & Persona Mapping** — screening criteria and quotas that map recruited participants back to the Phase 1 User Personas Document, including deliberate representation across trust/autonomy comfort levels, all three pillars (Productivity, Finance, Health), and assistive-technology users.
4. **Test Protocol Standards** — required structure for test scripts and task design (realistic task framing, think-aloud protocol, moderator neutrality rules) so findings are comparable across studies and not artifacts of inconsistent moderation.
5. **Synthesis & Insight Framework** — the standardized process for turning raw sessions into structured findings: affinity mapping, a severity rating scale (blocker / major / minor / cosmetic), and a required confidence rating tied to sample size.
6. **Feedback Loop into the Design System** — the defined intake path from a research finding to a change request against the Component Library (Phase 7, Doc 07) or Design Language, including how findings are triaged against the contribution process in Design System Governance (Phase 7, Doc 32).
7. **Special Research Tracks** — dedicated protocols for testing proactivity comprehension and trust (do users understand and trust actions the AI took without being asked), voice-specific usability testing coordinated with the Voice & Accessibility group (Phase 7, group 07), and assistive-technology usability testing.
8. **Research Repository & Knowledge Management** — where findings, session recordings, and past study reports are archived and made searchable, so design debates already settled by prior research are not re-litigated from scratch.
9. **Tooling & Participant Panel** — the testing platform(s), an always-on recruited participant panel spanning all three pillars and multiple trust levels, and incentive structure for repeat participation.
10. **Reporting & Stakeholder Communication** — the standard format and cadence for research readouts to design, product, and executive stakeholders, including how findings are distinguished from opinion in the readout.

## Deliverables
- Testing methodology decision matrix.
- Annual testing calendar with quarterly checkpoints and defined ship-gate triggers.
- Recruitment screener templates mapped to each Phase 1 persona and trust-level segment.
- Standardized test protocol and moderator script templates.
- Synthesis framework with severity rating rubric and confidence scale.
- Documented feedback-to-design-system intake process.
- Research repository structure and tagging taxonomy.
- Tooling and panel vendor selection with incentive model.

## Dependencies
Requires User Personas Document (Phase 1, Doc 5) and Success Metrics Document (Phase 1, Doc 6) as the source of what "success" and "who" mean for recruitment. Scoped against UX Metrics (Phase 7, Doc 31), which defines what gets measured quantitatively between testing waves. Feeds Design System Governance & Contribution Model (Phase 7, Doc 32) via the finding-intake process, and coordinates with Component Library (Phase 7, Doc 07), Design Language, and the Voice & Accessibility group (Phase 7, group 07) for method-specific protocols. Draws on the Proactivity Ladder Decision Engine (Phase 5, Doc 14) to define trust-testing segments.

## Teams
Design/UX Research, Design Systems, Product, Data/Analytics, Accessibility, Engineering

## Completion Criteria
- [ ] Methodology matrix covers every research method the team is expected to run, with explicit selection criteria for each.
- [ ] Recruitment screeners produce participant samples traceable to every Phase 1 persona, not just the most convenient-to-recruit ones.
- [ ] At least one full pilot study executed end-to-end (recruit → protocol → synthesis → design-system change request) before final sign-off.
- [ ] Feedback intake process is a named, documented path into Design System Governance's contribution process, not an informal handoff.
- [ ] Research repository is populated and searchable before program launch, not left for a "later cleanup."
- [ ] Signed off by: Head of Design (required), UX Research Lead (required), Head of Product (required).
