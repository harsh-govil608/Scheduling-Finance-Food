# Document 10: Calendar Service

## Document Name
Calendar Service

## Purpose
Define the architecture of the service owning calendar, event, and scheduling-state data — the system of record the AI Scheduler and Calendar Intelligence PRDs read from and write to. This document specifies the service's data ownership, external-calendar synchronization architecture, real-time propagation model, and scaling posture, without defining the AI logic that generates scheduling suggestions (Phase 5).

## Why It Exists
Calendar data sits at the intersection of three demanding requirements at once: it must stay consistent with external calendar providers (Google, Outlook, Apple) that the user also edits directly, it must support near-real-time propagation so the AI Scheduler, Notification Center, and widgets all see the same state, and it must resolve conflicts (recurring-event exceptions, concurrent edits, sync races) without silently losing user data. A dedicated architecture document is needed so these constraints are resolved once, at the platform level, rather than reinvented inconsistently by every feature that touches a calendar event.

## Approximate Page Count
9-11 pages

## Sections
1. **Service Boundary** — what this service owns (calendar, event, recurrence rule, attendee, external-calendar link) versus what it does not (tasks live in Task Service; scheduling intelligence/suggestions are generated by the AI layer and only land here as writes).
2. **Data Model** — calendars, events, recurrence rules and their exceptions, attendees, and the mapping table linking internal events to external-provider event IDs.
3. **External Calendar Sync Architecture** — the two-way synchronization model with third-party providers, including polling vs. webhook/push ingestion, sync-token/cursor handling, and how provider-side edits are reconciled into the internal model.
4. **API Surface** — operations exposed to the Gateway, the AI Scheduler integration boundary, and other backend services (e.g., Task Service creating a calendar block from a task).
5. **Conflict Resolution & Consistency Model** — how concurrent edits (client vs. external provider vs. AI-suggested change) are detected and resolved, and how recurring-event exceptions are represented so they don't desync from the base series.
6. **Real-Time Update & Notification Propagation** — how calendar changes fan out, event-driven, to Notification Center, dashboard widgets, and other connected clients within the platform's latency expectations.
7. **AI Scheduler & Calendar Intelligence Integration Boundary** — the contract by which the AI layer reads calendar state and proposes/writes changes, keeping this document's scope to the boundary rather than the AI logic itself.
8. **Multi-Region & Timezone Handling** — how events are stored and interpreted across timezones and DST transitions, and how a user's calendar data is placed given multi-region deployment.
9. **Scaling Characteristics** — peak-load patterns (day-boundary batch jobs, morning-dashboard reads, notification fan-out at reminder times) and their capacity implications at 100M+ users.
10. **Failure Modes & Degraded Operation** — behavior when an external provider sync fails or the service itself is degraded, including what the client is allowed to do locally (see Offline Mode PRD) before reconciliation.

## Deliverables
- Service boundary diagram distinguishing Calendar Service from Task Service and from the AI Scheduler integration layer.
- Entity-relationship diagram covering recurrence and exception modeling.
- External sync sequence diagrams (push/webhook and polling paths) per major provider category.
- API contract summary including the AI Scheduler write-back contract.
- Event catalog entries (e.g., calendar.event.created, calendar.event.conflict_detected).
- Conflict-resolution decision table (which side wins under which condition).
- Capacity model covering day-boundary and reminder-time peak load.
