# Document 37: Empty States

## Document Name
Empty States

## Purpose

Define the first-use and zero-data states across every major surface of the product — an empty task list, no transactions logged yet, no meals recorded yet — and specify how the product guides a new user productively through these moments instead of presenting a blank, lifeless screen.

## Why It Exists

Onboarding necessarily ends before any pillar has accumulated real data, which means the first sustained experience most users have with Productivity, Finance, and Health is an empty one — exactly the window in which the "time to first value" promised by the Onboarding Experience document must actually be delivered. An AI whose entire premise is that it remembers, predicts, and suggests has nothing to remember, predict, or suggest from yet in this window, so without a deliberate empty-state design, the product's most autonomy-driven pillars will look and feel the most broken at the exact moment a new user is deciding whether to trust it. This document exists so every empty surface is treated as an active design opportunity to guide the next action, not a placeholder screen left over from development.

## Approximate Page Count

6-8 pages.

## Sections

1. **Empty State Inventory** — the enumerated list of every major surface across all three pillars that can be empty or near-empty, so no surface is left undesigned.
2. **Empty State Philosophy** — the product's stance on what makes an empty state "productive" rather than merely decorative, tied to guiding the user toward the next concrete action.
3. **Per-Pillar Empty State Requirements** — the specific requirement for each pillar's primary empty surface (no tasks yet in Productivity, no transactions yet in Finance, no meals logged yet in Health), including what the state must communicate and prompt.
4. **Transitional / Partial-Data States** — the requirements for the in-between state where some data exists but not yet enough to produce a meaningful insight (e.g., three days of expense data, not yet a month), distinct from fully empty and fully populated states.
5. **Empty State Calls-to-Action** — how each empty state links back to the specific onboarding step, permission grant, or first action needed to populate it.
6. **Tone & Copy Requirements for Empty States** — the tone standard for empty-state copy, avoiding both cold placeholder language and overly cute copy that undermines the assistant's credibility.
7. **Empty States After User Action** — how the product distinguishes a "never had data" empty state from a "user cleared everything" empty state (e.g., all tasks completed, all suggestions dismissed), including appropriately different messaging for each.
8. **Cross-Pillar Consistency Requirements** — the shared visual and structural pattern every empty state across all three pillars must follow, so empty states read as one system.

## Deliverables

* Approved Empty States document.
* An empty-state inventory and requirements matrix covering every major surface per pillar.
* Distinct copy/tone guidelines for "never populated," "transitional," and "user-cleared" empty states.

## Dependencies

Requires the Onboarding Experience document (Document 31) for how empty states connect back to unfinished onboarding steps; requires the Product Pillars Overview (Document 02) and Information Architecture (Document 03) for the full surface inventory; requires the Product (Behavioral) Philosophy Document (Phase 1) for tone and the "one assistant" framing that empty-state copy must preserve.

## Which Teams Use This

Product, Design, Content/Copy, Growth.

## Completion Criteria

- [ ] Every major surface across all three pillars that can be empty has a documented, designed empty state.
- [ ] The distinction between "never populated," "transitional," and "user-cleared" states is applied consistently with no surface left ambiguous.
- [ ] Every empty state includes a clear call-to-action tied back to a specific onboarding step or first action.
- [ ] Copy and tone guidelines have been validated against at least one worked example per pillar.
- [ ] Signed off by: Head of Product (required), Head of Design (required).
