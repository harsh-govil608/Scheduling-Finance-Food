# ROLE

You are the Chief Product Officer, Chief AI Officer, Principal Product Architect, Distinguished Software Architect, Staff UX Designer, Principal AI Researcher, and Founder of a billion-dollar AI startup.

We have completed **Phase 1 (Company Foundation)** consisting of:

1. Vision & Mission
2. Product (Behavioral) Philosophy
3. Problem Statement
4. Market Definition
5. User Personas
6. Success Metrics
7. Guiding Principles

Those documents define **why the company exists**.

Now we are entering **Phase 2: Product Definition**.

The goal of Phase 2 is to completely define **what the product is**, before any engineering architecture, UI implementation, AI implementation, or coding begins.

This document is **NOT** the Product Definition itself.

It is the **Requirements Specification** for Phase 2.

Exactly like Phase 1 Requirements defined every foundation document, this document must define every Product Definition document.

---

# OBJECTIVE

Design the complete documentation structure for Phase 2.

Think like someone designing the documentation system for Apple, Stripe, Notion, Linear, OpenAI, or Google.

Do NOT think MVP.

Do NOT think startup shortcuts.

Assume this product will eventually serve hundreds of millions of users.

Every important product decision should have a dedicated design document.

---

# DOCUMENT FORMAT

For every document include exactly the following sections:

* Document Name
* Purpose
* Why It Exists
* Approximate Page Count
* Sections
* Deliverables
* Dependencies
* Which Teams Use This
* Completion Criteria

Maintain exactly the same quality and level of detail as the Phase 1 Requirements Specification.

---

# SCOPE

Your responsibility is ONLY Product Definition.

Do NOT include

* backend architecture
* infrastructure
* databases
* APIs
* AI implementation
* ML pipelines
* security implementation
* deployment
* business model
* marketing
* fundraising

Those belong to later phases.

Instead define the product itself.

# QUALITY REQUIREMENTS

The output should represent documentation standards expected inside a world-class software company.

Avoid shallow or merged documents.

If a topic deserves its own document, create one.

Optimize for long-term maintainability rather than minimizing document count.

Assume the documentation will guide hundreds of engineers and designers over the next decade.

---

# OUTPUT FORMAT

Generate:

# Phase 2 — Product Definition Requirements

For each document provide:

* Document Name
* Purpose
* Why It Exists
* Approximate Page Count
* Sections
* Deliverables
* Dependencies
* Which Teams Use This
* Completion Criteria

Organize the documents in the recommended writing order.

At the end include:

1. Total number of documents
2. Dependency graph between documents
3. Suggested documentation tree
4. Estimated total page count
5. Critical Path (documents that must exist before others can be written)
6. Review of completeness

Finally perform a self-review as if you were a Principal Product Architect.

List every important aspect of Product Definition that is still undocumented.

Continue adding documents until your review concludes that Product Definition is at least **99% complete** and no major product-domain decisions remain unspecified.

Optimize for building the most complete Product Definition documentation system possible for a category-defining AI Life Operating System.
